# Simulation and performance architecture

Source: `evidence/decompiled/` (Assembly-CSharp of RimWorld 1.6.4871, decompiled with ilspycmd 9.1; paths are namespace folders). All statements are **VERIFIED** in that code unless marked; numbers marked "model" come from `simulations/rimworld_model.py`.

## 1. The loop
- **Frame**: `Root_Play.Update` → `Game.UpdatePlay` (`Verse/Game.cs` 660–681): `TickManager.TickManagerUpdate()` runs the simulation ticks for this frame, then `World.WorldUpdate`, every `Map.MapUpdate` (region/room rebuilds, lords' per-frame update, weather, sky, flecks and all drawing), game components, signals and texture atlases. Simulation and rendering share one main thread.
- **Tick rate**: 60 ticks per real second at ×1 (`GenTicks.TicksPerRealSecond`). Speeds (`TickManager.TickRateMultiplier`, 74–113): Normal ×1, Fast ×3, Superfast ×6 (×12 while no player humanlike on any map is awake, `NothingHappeningInGame` 245–; ×18 with no maps), and a dev-mode-only Ultrafast ×15 (×150 with no maps or the dev boost; it has no button, `RimWorld/TimeControls.cs` 61, 147–151). A `TimeSlower` forces ×1 for 800 ticks whenever a verb that "causes time slowdown" fires (`Verse/Verb.cs` 339–341; 240 ticks for the short signal), so combat always plays at normal speed. Calendar: 2 500 ticks per hour, 60 000 per day, 15-day quadrums, 60-day years.
- **Per-frame budget** (`TickManagerUpdate`, 318–355): add the frame's real time to a debt (snapped to exactly one tick's time when the frame time is within 10 % of it), then run `DoSingleTick()` while debt remains, at most **2 × speed** ticks, and stop once **45.45 ms** have passed (`WorstAllowedFPS = 22`). Leftover debt is **discarded**. A smoothed tick-time average (720-sample moving average, then an EMA) feeds the UI's speed readout.
- **Consequence (model §1)**: with 8 ms of rendering per frame, a colony costing 2 ms per tick holds ×3 (180 ticks/s) at 80 FPS and ×6 (360) at 35 FPS, but ×15 falls to about 430 ticks/s; at 4 ms per tick even ×6 drops to about 210 ticks/s at 18 FPS. The game slows down instead of catching up, so a late-game colony simply runs at "×6 nominal, ×3 actual". The 10 % snap also lets a frame rate slightly above 60 FPS run ×1 slightly fast (62 ticks/s at 62 FPS in the model).

## 1a. Built-in measurement and runtime settings
- **Benchmark.** A debug action starts a 30-second benchmark (`PerformanceBenchmarkUtility.cs`, started from `Verse/DebugToolsMisc.cs` 325, checked each frame in `Root_Play.cs` 77). It reports frames per second, ticks per second and ticks per frame. Its message describes the budget rule in section 1: when the game cannot finish its target ticks within the budget, better performance raises the tick rate rather than the frame rate. That is the developers' own statement of the trade-off. Debug view settings also show TPS (min(1000 / mean tick time, 60 × speed)) and FPS counters (`RimWorld/GlobalControlsUtility.cs` 64–75).
- **Garbage collection.** `boot.config` sets `gc-max-time-slice=3`, i.e. Unity's incremental GC with a 3 ms slice per frame. This spreads Mono collections across frames instead of pausing, and fits the pooling in section 5 (VERIFIED value; its effect is STRONG INFERENCE).
- **Burst.** Burst-compiled code ships ahead of time in `Plugins/x86_64/lib_burst_generated.dll` (113 664 bytes), alongside `Unity.Burst`, `Unity.Collections` and `Unity.Mathematics` in `Managed/`.
- **Autosave** runs every `Prefs.AutosaveIntervalDays` × 60 000 ticks (at most one day in permadeath mode; `RimWorld/Autosaver.cs` 16–34). The autosave is queued as a long event with `doAsynchronously: false` (line 36), so the whole world is serialised through `Scribe` while play waits behind a "Autosaving" screen. `SafeSaver` writes to a temporary file and swaps it in, so a crash mid-save does not corrupt the old file.

## 2. What happens in one tick (`TickManager.DoSingleTick`, 357–499)
1. `Map.MapPreTick` for every map (`Verse/Map.cs` 933–965): item availability, haulables lister, auto-roof, roof collapse, wind, temperature, temporary drawers, then **`PathFinder.PathFinderTick`** (completes last tick's path jobs, schedules this tick's).
2. `ticksGame++` (fast-ecology debug adds 2 000).
3. The three thing tick lists (Normal, Rare, Long).
4. World-level ticks in order: date notifier, scenario, `World.WorldTick`, story watcher, game ender, **storyteller**, tale manager, quests, `World.WorldPostTick`.
5. `Map.MapPostTick` for every map (966–): wild animal and plant spawners, power nets, steady environment effects, terrain, gas, pollution, deferred spawner, **lords**, passing ships …
6. History, game components, letters, autosaver, filth monitor, transport ships.
Each step is wrapped in its own try/catch, so one failing subsystem logs and the tick continues.

## 3. Spreading work over time
- **Bucketed tick lists** (`Verse/TickList.cs`): a thing's `def.tickerType` is Never, Normal, Rare or Long. Rare things are hashed by `GetHashCode()` into 250 buckets and Long things into 2 000 buckets; each tick runs exactly one bucket (`TicksGame % interval`). 5 000 rare things therefore cost about 20 `TickRare()` calls per tick (9–33 in a random hashing, model §2) instead of 5 000 calls every 250th tick. Registration and deregistration are deferred to the start of the next list tick.
- **Hash-offset intervals** everywhere: `IsHashIntervalTick(n)` staggers periodic checks by an id-derived offset (`HashOffset` = `HashCombineInt(id, 169495093)`), e.g. needs every 150 ticks, the constant think tree every 30, mental-break checks every 150, social checks every 60.
- **Camera-dependent interval ticking (new in 1.6)** (`Verse/Thing.cs` `DoTick` 700–751; `GenTicks.GetCameraUpdateRate`): Normal-ticker things run `Tick()` every tick for things that must be smooth (movement, verbs, stances, job drivers, health), and accumulate `tickDelta` for `TickInterval(delta)`, which runs every `clamp(UpdateRateTicks, 1, 15)` ticks: **zoom level + 1** when on screen in the current map, **15** when off screen or on another map. Periodic logic is written against the delta (`IsHashIntervalTick(period, delta)`, `IsTickIntervalDelta`) so it stays correct at coarse rates. Off-screen pawns thus do their interval work at 1/15 of the per-tick frequency (model §2).
- **Pawn split** (`Verse/Pawn.cs` `Tick` 1538–1617, `TickInterval` 1618–): every tick — pather, verbs, stances, job driver, health, equipment, abilities, inventory, genes, ambient sounds, effecters; interval — job tracker checks, health interval, mind state, carry, infection, needs, apparel, interactions, calls, skills, drafter, relations, psychic entropy, story/ideo trackers.
- **Storyteller cadence**: incident generation runs once per 1 000 ticks (60 checks per day, `Storyteller.StorytellerTick` 213–224); the incident queue ticks every tick.

## 4. Parallel and asynchronous work
The simulation itself is single-threaded. Parallelism is used where work can be isolated:
- **Pathfinding (new in 1.6)** (`Verse/PathFinder.cs`, `PathFinderJob.cs`, `PathFinderMapData.cs`, `PathGridJob.cs`): callers create a `PathRequest`; requests are queued and processed in `MapPreTick`. Map data is gathered (sources in `Parallel.ForEach`), one **cost-grid job** (`IJobParallelFor`) is scheduled per distinct grid request (traverse parameters, avoid grid, tuning, allowed area; cached and reused by key), then a **Burst-compiled A\* job** (`[BurstCompile] struct PathFinderJob : IJob`) per request, chained after a door-blocked job. Jobs complete at the start of the next `PathFinderTick`, which resolves each request; a synchronous `FindPathNow` remains for code that needs an answer immediately. Native buffers (`NativeArray`, `NativePriorityQueue`) are allocated persistently and recycled between batches.
- **Rendering**: `DynamicDrawManager` culls and computes silhouette matrices with Burst `IJobParallelFor` jobs and runs a managed parallel pre-draw; `GlowGrid` computes and combines light grids in jobs; the fleck system draws batches on the thread pool (`FleckSystemBase`, `FleckParallelizationInfo`).
- **Loading**: XML parsing, def loading and static constructors use parallel loaders (`DirectXmlLoader`, `LoadedModManager`, `GenThreading`).

## 5. Spatial acceleration
- **Regions** (`Verse/Region.cs` `GridSize = 12`, `RegionMaker`, `RegionGrid`, `RegionLink*`): walkable space is flood-filled into regions that never cross a 12 × 12 grid square, connected through links along their edges; regions group into districts and rooms (`RegionAndRoomUpdater`). A 250 × 250 map has at least 441 squares (model §4). Changes mark cells dirty; regions and rooms are rebuilt lazily in `MapUpdate` (`TryRebuildDirtyRegionsAndRooms`), and the grid validates 16 squares per frame (`CleanSquaresPerFrame`).
- **Reachability** (`Verse/Reachability.cs` `CanReach` 102–): an immediate-adjacency check, then "same district" as an O(1) shortcut, then a region flood fill between source and destination regions; results are cached by the unordered pair of region-group ids plus traverse parameters (`ReachabilityCache`).
- **Closest-thing search** (`Verse/GenClosest.cs` 12, 40–86): breadth-first over regions using per-region thing listers, up to 30 regions by default, then (if allowed) a global scan of the map's lister for that `ThingRequestGroup` with a reachability check per candidate. Work scanners use this for nearly every job search.
- **Listers and caches**: `ListerThings` indexes things by 82 `ThingRequestGroup`s; `ListerHaulables`, `ListerBuildings`, attack-target caches and item availability keep frequently asked questions cheap. Stat values have an immutable cache (`ConcurrentDictionary`) for stats that never change and a staleness-checked temporary cache for `cacheable` stats (`RimWorld/StatWorker.cs` 15–64; e.g. mental-break threshold reads with a 5-tick staleness).
- **Mesh sections**: the map is drawn in 17 × 17-cell sections (`Verse/Section.cs`) that are regenerated only when dirtied by a change flag.
- **Pooling**: jobs, toils and many temporary lists are pooled (`Verse/JobMaker.cs` and `ToilMaker.ReturnToPool`, called from `Pawn_JobTracker`; `SimplePool<T>` for lists) to cut garbage-collection pressure on the Mono runtime.

## 6. Scaling hot spots seen in the code (STRONG INFERENCE)
- `ReservationManager.CanReserve` (157–227) walks the map's whole reservation list for every query, so its cost grows with the number of active reservations × reservation checks per job search.
- `JobGiver_Work` can call region searches for every work giver in a priority tier on every job search; idle pawns re-search when they finish jobs, so many idle pawns with many work types multiply this.
- Pathfinding is cheaper per request since 1.6 but every request still pays a cost-grid job unless another request this tick used the same grid key.
- The frame budget (45 ms) is shared with rendering, so a heavy map at ×6 trades FPS for speed until both drop.

## 7. Determinism and randomness
`Verse.Rand` is a counter-based generator: `Value = (MurmurHash(seed, iterations++) + 2³¹) / 4 294 967 295` (`Verse/Rand.cs` 35; `Verse/MurmurHash.cs`). The global seed comes from the wall clock at start-up and is not saved, so reloading a save re-rolls ordinary randomness. Subsystems that must be reproducible push a derived seed (`Rand.PushState(seed)`; 98 `PushState` call sites, 46 with an explicit seed): the storyteller's on/off-cycle incident schedule, a lord's state graph (`loadID × 193`), auto-flee thresholds, many seeded ranges. The C# port check in `experiments/rngcheck/` confirms the Python and JavaScript re-implementations match the decompiled functions bit for bit.
