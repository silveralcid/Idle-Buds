# Architecture

Build examined: Steam app 1476970, `LegendsOfIdleon.exe` (Electron 11.5.0, Chrome 87), `resources/app.asar` (126 MB). Client game build 144 (it accepts server `GameVERSION` 143 or 144; 9999 shows a maintenance popup, `N.pretty.js` 153456–153555). Nothing was run, no account was used and no Firebase endpoint was contacted; everything below is read from the shipped files.

## The game as a Stencyl project
- **Behaviours and scenes.** Game logic lives in 64 `ActorEvents_N` behaviour classes, 162 `SceneEvents_N` classes and `Design_23_23_EveryScene`; names are Stencyl's numeric ids, not descriptive.
- **Custom blocks as the rule library.** 240 static definitions named `_customBlock_<Name>` (239 names, 235 non-empty) (e.g. `DamageDealed`, `AFKgainrates`, `IncreaseExpREQ`, `StampCostss`) hold the formulas. Most take a **string selector** and branch on it (`SkillStats("MiningEfficiency")`, `ArbitraryCode("HitChancePCT")` with 33 literal branches plus a `StatueBonusGiven` prefix and 68 distinct selector strings at call sites; `EtcBonuses("47")`, a map lookup over 108 bonus ids), so one function is many formulas.
- **Game attributes as the state store.** All state is in Stencyl game attributes read with `a.engine.getGameAttribute("Name")` (character levels `Lv0`, `ExpReq0`, `TimeAway`, `OptionsListAccount`, `GemsOwned`, `DNSM` scratch map …). Temporary results are written into scratch maps (`DNSM`, `DummyNumbersStatManager`) and read back, which is how visual scripts pass values.
- **Data as code.** Content is not loaded from files: `ItemDefinitions` … `ItemDefinitions6` build 2 480 items through `addNewEquip`, `addNewConsumable`, `addNewQuest` (1 020 calls) and `addNewItem` (36) calls, `MonsterDefinitions.make()` adds 418 monsters and resources, and `CustomLists`, `CustomLists2`, `CustomLists3`, `CustomMaps(REAL)` are 260 zero-argument functions that return the tables (maps, talents, bubbles, stamps, cards, gem-shop pages …). `tools/dump.js` evaluates these classes alone in a `vm` sandbox with a one-line stub for Haxe's `StringMap` and gets every table without running the game.
- **Haxe/Stencyl idioms** recognisable in the output: `StringMap` as `new l` with `.h`, `Std.string` as `h.string`, Stencyl `c.asNumber`, `Y.thrown`, `A["scripts.X"] = X` class registration.

## Online backend (VERIFIED from client code; server side not observed)
- **Firebase project `idlemmo`**: Firebase Auth; Cloud Firestore for saves (`_data/{uid}`), server variables (`_vars/_vars`), guild stats (`_guildStat`), raffles (`_raffleStore`, `_raffleStore2`), tournaments (`_TOURNAMENT`, `_T_…`, `_T_RES_F…`) and raids (`_RD_…`); Realtime Database (two instances, the second for parties) for presence (`_usersOnline`), movement, chat, friends, guild and party events; Cloud Functions called through `firebase.functions().httpsCallable`.
- **The bridge.** The game never touches Firebase directly. `FirebaseStorage` (`N.pretty.js` 335–) calls `window.React.createElement(name, args)`; `firebase.js` replaces `window.React.createElement` with a dispatcher that reverses the command name, base64-encodes it and looks it up in a table of 174 handlers (`init`, `beginSave`, `commitSave`, `requestTime`, `getServerVarLoad`, `buyCompanionBox`, `sendTradeOffer`, `registerForTournament`, `purchaseLevelUp` …). Cloud Function names are two- to five-letter codes (55: 54 called through `useState` and `getLoot` called directly; e.g. `ttg`, `sil`, `ptc`, `ptf`, `gc`, `pkab`), called through a function renamed `useState`. The naming is camouflage, not protection: it is plain JavaScript in the shipped file.
- **Saves are written by the client.** `commitSave` does `firestore.collection("_data").doc(uid).set({...entries}, {merge: true})`; the game assembles 177 save keys (levels, inventories, bank, `GemsOwned`, `GemItemsPurchased`, `BundlesReceived`, `TimeAway` …) in `CloudSAVE` (`N.pretty.js` 74369–74416; `SaveGamee`, 67319, writes no keys itself). What the server validates (Firestore rules, functions) is not visible.
- **Server-authoritative pieces.** The time reference (`ttg` → `TimeAway.GlobalTime` at login and on each re-sync; see "Clock trust" below), purchases (on Steam, `startBuy` calls `ptc` with the Steam-ID bundle from `extra_steam.js`, and Steam's `micro-txn-authorization-response` → `window.confirm` → `ptf`, `wrapper/steam.js` 32–45; `index.html` also loads Stripe.js for a web flow that was not traced), gem and bundle grants (server-set `ServerGems` and `bun_*` flags that the client turns into currency and items), loot rolls for some enemies (`getLoot`), companions (gacha boxes, raffle tickets, trades), tournaments, raids, votes, guilds, friends, chat.
- **Live tuning.** 66 server variables (`getServerVarLoad`): `GameVERSION`, happy hours, event flags, gem-bundle offers, research EXP scaling `A_ResXP`, arcade rotation, vote categories, Twitch-live flag …
- **Multiple sign-in handling.** Presence entries carry a random `deviceId`. `firebase.js` forwards a `DUP_LOG` server message only when it carries this device's id, and the game then switches to scene 10 (`N.pretty.js` 120992–120997). The grey-out (opacity 0.5) and the "MultipleSignIn: Cancel saving data" path fire on a different condition: a uid change during `completeLogin` ("Possible Double Sign In").

## Time, ticks and offline
- The game runs on Stencyl's frame loop (OpenFL `requestAnimationFrame`); per-second work happens in `1second`/`5sec` custom blocks; timers count down `TimeAway` fields and per-monster respawn arrays.
- **Offline is a formula, not a replay.** On returning, each character's away time (server time − its `TimeAway.Player` stamp) is fed to `AFKgains` for the activity it was left on (fighting, mining, choppin, fishing, catching, cooking, lab, divinity, spelunking, worship charge …), using analytic hourly rates × AFK gain rate; account-wide systems (anvil production, refinery, traps, cauldrons, construction, printer, shop restock …) are advanced by `AFKcode`/`AwayTimers` with the same elapsed time. There is no batch replay of ticks.
- **Clock trust is partial.** `TimeAway.GlobalTime` is set from server time at login (`N.pretty.js` 153257, 160971) and then advanced locally: +1 each second in `_event_Every1sec` (121052), and on regaining focus after a gap of 0–120 s by the local wall-clock gap, which also runs `AwayTimers` (120932–120935). Only gaps over 120 s trigger a new server sync (`requestTime`, 120912/120931). Changing the local clock therefore cannot fabricate a long absence, but the game uses local time between syncs.
- **Caps.** `AFKgains` (68980–69037) applies the Unending Energy prayer cap (36 000 s) and resets the gap when the character stamp is below 10⁴ or the gap exceeds 2·10⁸ s; `AwayTimers` skips gaps of 10⁸ s or more. Account systems cap their own stores in `AFKcode` (anvil `AnvilProduceStats("Cap")`, forge input amounts, `WorshipChargeMax`, Dream `BarFillReq`). The claim actor (`ActorEvents_209`, about 71060–71250) puts ores, logs, fish, bugs and crafted items into the chest (stack cap 1.05·10⁹, overflow converted to atoms) and drops everything else on the map. Whether the server bounds any of this is unknown.

## Persistence details
- 177 key names; lists saved through `addSaveEntryList`/`JsonList`/`SparseList`/`Map`; per-character keys get the character slot appended (`"Lv0" + DummyText3`, `"AFKtarget" + …`), account keys are unsuffixed.
- Saving runs `CloudSAVE` then `SaveGamee` on events (character switch, play button, purchases …) and on a timer: `_event_Every1sec` (121052) increments `CloudSaveCD[0]` and saves once it passes 240, about every four minutes, except in dungeons, the tutorial and maps 20–23.

## Observations
- The architecture is a visual-scripting game scaled far beyond its tool: one 25 MB script, string-dispatched formula blocks with hundreds of additive terms, and content as executable code. It works, and it ships a very large game from a small team, but every formula is a long chain of named lookups (see `evidence/blocks/DamageDealed`: about 150 sources in one function).
- Responsibility is split unusually: the server owns time, money in, loot for some enemies and social state, while the client computes and writes progress. That keeps server cost low for an idle MMO with millions of characters, at the price of trusting the client for most progression (INTERPRETATION; server-side checks unknown).
