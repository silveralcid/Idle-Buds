# Idle Buds MVP: detailed execution playbook (companion to the active plan)

This companion operationalizes M0–M9 in the [canonical execution plan](mvp-execution-plan.md), not a second backlog or additional features. Owner requested deeper execution planning, strong reuse, bounded experimentation and an end-to-end testable MVP. Target is the first usable integrated multiplayer candidate and experiments, not public beta, commercial polish, mature scale or complete level-99 content. All budgets, numerical baselines, task slices and choices below are **proposals** until scope approval; no implementation gate is lifted. Mechanical choices consistent with approved design can be provisional and reversible; material changes to design or scope require owner decision.

### Stop rules and work discipline

- Before each task: specify one player-visible outcome, inputs/contracts, owned paths, existing references, exclusions, executable PASS criteria, and stop point. Read only the applicable sources; reuse the existing repo tools, issue/PR and evidence conventions. One integration lead owns dependency order. Avoid a second project tracker.
- Reuse ladder: ADOPT existing own code/config/assets or a small maintained licensed library if fit; ADAPT independently implemented established patterns and rights-cleared components; BUILD the smallest Idle Buds-specific rule only when the first two are worse. Search for at most 30–60 minutes per decision (proposed cap), compare no more than two serious candidates, document source/version/rights/why in PR or actual owner. Stop when one meets the task. No framework bake-offs.
- Candidate qualification: verify exact version/license, transitive dependencies, maintenance/security, TypeScript/Node 24 compatibility, real behavior and integration burden; pin chosen version in lockfile, keep notices and tests. For a reference pattern cite the exact source, uncertainty and original implementation boundary. Public availability does not grant code/assets rights; use proprietary reverse-engineering findings for behavior/hypotheses only. Never import donor extracted files, IP, code or data. Avoid a large dependency merely to reuse one trivial algorithm.
- Each implementation packet is targeted at one small reviewable PR, generally one to two focused working sessions; split by player outcome if larger, not into needless layers. Proposed experiment limit: 2 variants plus baseline, fixed seeds/fixtures, one working day maximum, one repair/retest cycle for each experiment. An observed integrity/security bug is a hard stop, not a license to waive the requirement; isolate and escalate after two focused repair attempts without new evidence. If no result, adopt safe simplest fallback within approved design or HOLD decision. No endless "improve" passes. Stop on PASS, merge only with authorization and verified relevant checks. Unrun tests are NOT RUN.
- Do not use timeboxes as artificial deadlines or claim effort estimates without actual throughput. At M1 record actual packet throughput; use it to refine remaining work, not to enlarge scope. New feature proposals go to existing Incubator. No unapproved public/paid services, migrations of real data, commissions or deploys.

### Candidate reusable components, not blanket dependency approval

Keep current React/Vite/TS/npm, lint, Playwright, Python repo helper and CI; no rewrite. At M1 use Fastify route schemas and plugins; prefer [node-postgres](https://github.com/brianc/node-postgres) plus [node-pg-migrate](https://github.com/salsita/node-pg-migrate) for real PG SQL/transactions and migrations. Avoid ORM-plus-query-builder stacks or hand-built migration engines. Use one secure auth/session approach: qualify official [Fastify secure-session](https://github.com/fastify/fastify-secure-session) (encrypted cookie, explicit session revocation/expiry checks where needed; verify CSRF and compatibility) versus a maintained established auth solution if it better handles lifecycle. For private testing use invite-only test accounts and existing password/identity library or managed service only if authorized; no custom cryptography/password schemes. Use [Fastify rate-limit](https://github.com/fastify/fastify-rate-limit) when exposed. Reuse standard Node crypto for secret seeds; evaluate [seedrandom](https://github.com/davidbau/seedrandom) for deterministic simulation (not cryptographic security); keep seeds and mutable RNG state server-owned. Existing Vitest recommendation, Playwright and [fast-check](https://github.com/dubzzz/fast-check) for property tests when invariants justify it. For PvP use standard Elo baseline and one simple rating/progression band selector, not novel rating research. For art prefer verified owned packs and [Kenney CC0 assets](https://kenney.nl/support) with per-pack rights records. No entire external game framework or general battle engine. Source URLs checked in planning; no packages installed or compatibility/rights audits completed. PokéClicker and pret/pokeemerald had no recognized repository license in GitHub metadata at review, so reference-only unless specific rights verified. Showdown server MIT does not license third-party Pokémon IP. Package-specific notices and production asset rights must be checked at adoption. Current repo is public.

### Minimal runtime shape and interfaces (not a new framework)

Maintain one npm project, one web app, one backend, one PG database. Use current src/game for pure rules, src/data for stable typed data, server for authoritative HTTP, transactions and account state. Create domain files only when needed (activities, progression, combat/capture, breeding, market, social, ranked). React state/requests and CSS suffice; adopt a query/cache library only if repeated real request complexity warrants it. No monorepo, event sourcing, CQRS, generic ECS, game scripting DSL, service mesh, redis, message broker, native shell, editor suite or speculative analytics stack. Local PG via documented local instance or a minimal Compose service if already available and simpler. Production deploy not part of first local test.

- Commands: validate actor, payload, current state and eligibility, reconcile affected activities, apply mutation and commit receipt/checkpoint/reward atomically. Read queries return view models, effective rates, relevant unlocks, selected activities and results. Server seeds from secure entropy; deterministic random stream/counter per committed activity or battle with version; no future seeds exposed. A stable command ID, account lock where needed and unique receipt make retries safe. Resource/currency counts bounded safe integers; use explicit units and rounding, avoid floating accumulation; store PostgreSQL bigint safely across JSON if needed. Use real SQL constraints on ownership, nonnegative balances, FK/reference integrity and unique receipt; lock multiple participants in deterministic order. No blanket distributed locks.
- Activity contract: start/pause/change assignment, due completion times, remainder, output/input deltas and stop reason. One pure advance(state, elapsed/server boundary, data/version, seed/counter) used for ordinary progress and catch-up; batch identical deterministic cycles only when equivalence proven, preserve partial cycle, cap/grace/input/full-storage/finite constraints. No reward on invalid clock or twice for a repeated claim. Stop safely, show why, resume explicitly according to qualified policy. At first use of a new activity verify partition invariance and one completion at boundary.
- Battle contract: resolve(snapshotA, snapshotB, rulesVersion, serverSeed) -> bounded outcome plus ordered events. Sim never calls browser, DB, network, wall clock or global random; version and freeze inputs, run same resolution for PvE/PvP; animation is an optional presentation of returned events. Tie/order/termination rules explicit. Keep Attack/Health integers and small set of typed trigger/effect cases only used by roster, no unbounded recursive trigger chain; golden fixtures for simultaneous defeat, commander entry, support, stalled battle, capture outcome. Combat preview uses known public stats, not hidden seed.
- Unique instances: Bud, gear, egg identity and owner immutable IDs; ownership moves atomically, same instance cannot be escrowed twice; define work/breeding/formation lock policy before concurrent systems use it. Proposed simplest conservative default: work/breeding commitments mutually exclusive; block transfer/release/condense while committed or in an active encounter; ranked defense snapshot is immutable, not a live lock. Approve exact combat/production coexistence and snapshot freshness before M3. No irreversible loss without explicit confirmation. One inventory capacity rule selected when it affects real behavior, not a generic item container architecture.
- Playtest configuration: original typed data constants or validated JSON with content version, no runtime authoring platform. Keep seeded test accounts/fixtures separate from real progression, dev-only setup script protected from public use. Inject clock through test service, not a user-facing time skip or production client override. One local setup, seed/reset (test DB ONLY with unmistakable guard), smoke, test, and deterministic sim commands registered using repo tooling when they exist. A test environment can use accelerated fixture time; normal-mode onboarding/daily tests always use actual proposed player timing.

### Provisional balance and content starting point (test inputs, not permanent game design)

Start data-small and grow to the fixed counts; no exhaustive design work up front. For M1 choose two or three original useful starter species within eventual 15, one early Earth encounter, a simple gather->craft->capture chain. Proposed baseline for testing only: action intervals 3–10 s, starter chain 2–3 ingredients, early fights roughly 10–20 s, first-catch eligible pool high enough to achieve the approved five-minute target; quantify with paired seeds rather than promising exact odds. Select one explicit capture formula with species difficulty, item tier and Tender progression and clamp to 0..1; start with an inspectable table/linear adjustment, not a complicated nonlinear curve. First useful unlocks at low skill levels; use one monotone hybrid XP table with quick early gains and slower tail, one independent Bud XP table, no XP exploits; do not author max-level content. Keep level-99 cap. Three tiers of content with early-to-midgame paths, no extra tier. Use a small shared stat budget per progression band, fixed species aptitude eligibility, individual IV/trait/level modifiers. Choose bounded integer IV/stat scales and explicit rounding at M3; test comparative value and no universally dominant Bud.

For capture filter choose an ordered list of simple conditions (new species, rarity, species/affinity, optional individual quality only if visible/eligible), then item-or-skip. Proposed first-match, deterministic target order, unavailable item stops/skips with visible reason; qualify before M3. No arbitrary expression language. For combat begin with a small set of triggers/effects (battle start, frontline hit, defeat, ally support; bounded damage, attack/health changes, simple buffs); only introduce new primitive if a planned species/gear needs it. Do not add arbitrary scripting. Proposed single baseline battle max event/round budget with explicit tie/draw, exact values from lab. Gear and trait ranges data-driven, no reroll system. For breeding use simple compatibility groups and sex exceptions, independent draws from parents/random; start with one slot, one incubation queue, one optional enhancement, no third species. Exact IV probabilities and timers qualify at M4. NPC spread, tax and restocks test low-liquidity behavior; conservative starter goods only, no Buds, no dynamic pricing. Clan one bonus and one goal; ranked one format and prestige badge/title. These are deliberately minimal, reversible values/models; any materially different approved design requires owner approval. No placeholder mechanics in the final integrated build.

### Testability package and bounded experiments

Deliver three ways to play/test with the same game rules: (1) clean local account, real normal-time onboarding; (2) disposable two-account integration fixture with early/midgame progress, genuine trades/clan/PvP; (3) deterministic headless fixtures for rapid time advancement and repeated balance comparisons. Build local test-only setup/seed/reset instructions, no dev cheats reachable by ordinary/public clients, no touching real player data. One minimal CLI/script or test runner with named fixtures is enough; no admin dashboard, scenario platform, live-ops console, spreadsheet simulator framework or separate game engine. Existing evidence directory/PR links record commit, versions, fixture/seed, actual timings/outcomes, failure reproduction and disposition. For all paired experiments use same inputs/seeds, report distributions/percentiles and complete outcomes, including failures. Never mistake simulation for human fun.

### Definition of ready-to-playtest vs definition of product success

**Candidate READY (binary):** all must-ship core pillars exist and are actually reachable; all packet engineering checks and relevant canonical acceptance matrix correctness/security checks pass on same named commit; reproducible local/private test environment and clean resettable fixtures; a real browser player and two-account E2E prove catch -> work -> offline -> breed -> trade -> cooperate -> ranked. All 15 species, 3 zones, 3 tiers, 4 affinities and 7+4 skill tracks, initial early/midgame content, and placeholder rights documented. Core flows mobile/desktop, no known data-loss/dupe/ownership exploit or critical blocker; restore tested. Testable build includes the source, locked install, migration, test-account setup, how to launch, known limitations, release/version and evidence. Engineering performance goals are proposed measured baseline, not a scale promise. No external service or public launch required.

**Playtest outcomes (diagnostic):** evaluate the proposed timings, balance, voluntary returns, and qualitative enjoyment in the [canonical acceptance matrix](mvp-execution-plan.md#acceptance-matrix-proposed-numerical-gates-owner-approves-before-build-tune-only-through-explicit-decision) and experiments. They are not logically prerequisites to being able to start a playtest. If a target misses, record failure and bounded change or owner-approved tradeoff; no silent pass, no indefinite polish. Internal test candidate is complete once engineering gate passes and owner can play. A later public beta/official launch requires separate owner approval, evidence, rights and deployment/operations readiness. Never infer commercial success from ten players. M0 still requires separate release scope approval and BEAT BAES gate; this remains planning-only.

### Practical first playtest itinerary (M9, after approval/build)

- Normal first session: fresh account, read activity, gather/craft, fight, catch, assign, close browser. Return after normal/fixture-controlled time; inspect rewards, choose next goal. Record timing and confusion without coaching.
- Progressed fixture: try all 7 skills, two different Bud jobs, tool upgrade, unlock by combat or production, capture filter and repeat/stop combat, compare team compositions. Breed compatible pair, hatch, inspect IVs and traits. Player B sells a resource and individually owned Bud; A places a buy order, both settle/cancel; verify owners/balances. Use chat/friend/clan contribution and blind PvP. Test portrait/landscape plus keyboard navigation. Return after simulated capped elapsed time via test-only clock. No live purchases.
- Record one short result per test: expected, actual, pass/fail, evidence, severity, fix or hold. Fix integrity/crashes/progression blockers first, then small friction. Ask owner whether full ecosystem deserves another bounded iteration or release qualification; do not build more content automatically.
